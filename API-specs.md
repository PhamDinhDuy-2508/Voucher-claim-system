# Voucher Claim API Specification

## 1. Conventions

- Base URL: http://localhost:8080
- Media type: application/json
- JSON properties use camelCase and timestamps use ISO 8601 UTC.
- Campaign IDs are UUIDv7 strings generated by the server.
- User, merchant, and campaign IDs are opaque strings. The API checks presence, not length or format.
- Idempotency keys are opaque client-generated strings.
- Merchant endpoints use X-Merchant-Id. Internal endpoints use X-Internal-Token.

## 2. Endpoint Summary

| Method | Path | Purpose |
|---|---|---|
| POST | /v1/voucher-campaigns | Create a draft campaign |
| POST | /v1/voucher-campaigns/activate | Activate a campaign and create inventory slots |
| POST | /api/v1/claims | Submit a durable claim request |
| GET | /v1/voucher-claims/me?campaignId={id} | Read the user's successful claim |
| PUT | /internal/v1/user-scores/{userId} | Store a trusted score snapshot |

Errors use:

    {
      "code": "ERROR_CODE",
      "message": "Human-readable description",
      "timestamp": "2026-08-28T12:56:00Z"
    }

## 3. Create a Campaign

    POST /v1/voucher-campaigns

Required headers: Content-Type: application/json, X-Merchant-Id, and Idempotency-Key.

Request:

    {
      "name": "Launch campaign",
      "totalQuantity": 1000,
      "startsAt": "2026-08-28T12:00:00Z",
      "endsAt": "2026-08-29T12:00:00Z"
    }

Response — 201 Created:

    {
      "campaignId": "0198f13a-8c00-7a91-8bc1-41dd31a250ab",
      "merchantId": "1234567890123456",
      "name": "Launch campaign",
      "totalQuantity": 1000,
      "status": "DRAFT",
      "startsAt": "2026-08-28T12:00:00Z",
      "endsAt": "2026-08-29T12:00:00Z"
    }

An exact replay returns the stored result with 200 OK. The server does not compare request hashes; a client must not reuse one key for another logical operation.

| Status | Code | Meaning |
|---:|---|---|
| 400 | VALIDATION_ERROR | Campaign data is invalid |
| 409 | IDEMPOTENCY_CONFLICT | Key belongs to an incompatible operation |

## 4. Activate a Campaign

    POST /v1/voucher-campaigns/activate

Required headers: Content-Type: application/json, X-Merchant-Id, and Idempotency-Key.

Request:

    {
      "campaignId": "0198f13a-8c00-7a91-8bc1-41dd31a250ab"
    }

Response — 200 OK:

    {
      "campaignId": "0198f13a-8c00-7a91-8bc1-41dd31a250ab",
      "status": "ACTIVE",
      "totalQuantity": 1000
    }

Activation creates inventory slots in bounded batches. Replaying the operation is safe.

| Status | Code | Meaning |
|---:|---|---|
| 404 | CAMPAIGN_NOT_FOUND | Campaign does not exist for this merchant |
| 409 | INVALID_CAMPAIGN_STATE | Campaign cannot transition to ACTIVE |

## 5. Submit a Claim

    POST /api/v1/claims

Required headers: Content-Type: application/json and Idempotency-Key.

Request:

    {
      "userId": "1234567890123456",
      "campaignId": "0198f13a-8c00-7a91-8bc1-41dd31a250ab"
    }

Response — 201 Created:

    {
      "requestId": "claim-request-uuid",
      "campaignId": "0198f13a-8c00-7a91-8bc1-41dd31a250ab",
      "userId": "1234567890123456",
      "status": "PENDING"
    }

This response acknowledges durable admission; allocation continues asynchronously. An exact replay returns 200 OK with the original request.

Redis stores only a short-lived positive replay. A cache miss always continues to MySQL; it does not prove that the key is new. MySQL uniqueness is authoritative.

| Status | Code | Retry? | Meaning |
|---:|---|---:|---|
| 400 | VALIDATION_ERROR | No | Required data is missing |
| 404 | SCORE_NOT_FOUND | No | No trusted score exists |
| 409 | ALREADY_CLAIMED | No | User already owns a campaign voucher |
| 410 | CAMPAIGN_NOT_ACTIVE | No | Campaign is not claimable |
| 429 | TOO_MANY_REQUESTS | Yes | Admission limit was exceeded |
| 503 | BUSY | Yes | Inventory may exist, but slots are currently locked |

SOLD_OUT is terminal and differs from BUSY. An empty SKIP LOCKED result alone is not proof that inventory is exhausted.

## 6. Read My Claim

    GET /v1/voucher-claims/me?campaignId={campaignId}

Response — 200 OK:

    {
      "claimId": "claim-uuid",
      "campaignId": "0198f13a-8c00-7a91-8bc1-41dd31a250ab",
      "userId": "1234567890123456",
      "voucherCode": "VC-A1B2C3D4E5",
      "status": "SUCCEEDED",
      "claimedAt": "2026-08-28T12:56:30Z"
    }

A missing result returns 404 CLAIM_NOT_FOUND.

## 7. Store a Trusted Score

    PUT /internal/v1/user-scores/{userId}

Required headers: Content-Type: application/json and X-Internal-Token.

Request and response:

    {
      "userId": "1234567890123456",
      "score": 800
    }

The request body only requires score; the response also contains userId. The claim service snapshots this value at admission, so later changes do not reorder an accepted request.

## 8. Claim States

| State | Meaning | Terminal |
|---|---|---:|
| PENDING | Persisted and waiting for publication/materialization | No |
| QUEUED | Present in the campaign priority queue | No |
| PROCESSING | Leased by a claim worker | No |
| RETRY_WAIT | Temporarily failed and recoverable | No |
| SUCCEEDED | Voucher allocated | Yes |
| REJECTED | Terminal business rejection | Yes |

## 9. Retry and Priority Contract

- Reuse the same Idempotency-Key after timeouts and connection failures.
- Never reuse a key for another user, campaign, or operation.
- Retry 429, 503, and transport failures with exponential backoff and jitter.
- Kafka and recovery are at-least-once; database constraints preserve one logical result.

Redis orders currently queued campaign requests by descending score. If A=800, B=200, C=100, and D=0 are present when the scheduler pops, dequeue order is A, B, C, D.

This is best-effort, not strict global priority. Kafka arrival timing, the finite collection window, and parallel database transactions can cause a lower score to commit shortly before a higher score. Strict priority would require a durable closing window and ranked, serialized allocation.
